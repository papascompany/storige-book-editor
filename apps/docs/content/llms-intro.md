# Storige 파트너 문서

> Storige 플랫폼(인쇄물 편집기 · PDF 검증 · PDF 합성)에 외부 서비스를 연동하기 위한 공개 문서. 연동 유형 3종 결정 매트릭스, 공통 기반(인증 · 파일 한도 · 에러 · 레이트리밋), Partner API v1 레퍼런스를 담는다.

- **Partner API v1 base URL**: `https://api.papascompany.co.kr` — 모든 v1 경로는 `/api/v1/*` 이고, 무인증 라우트는 0건이다.
- 이 사이트는 연동 가이드(`docs/PLATFORM_INTEGRATION_GUIDE.md`)의 **발행 채널**이다. 규범 서술의 정본은 가이드 본문이고, 아래 규칙은 그것을 기계가 읽기 좋게 요약한 것이다. 규칙과 본문이 어긋나 보이면 **본문이 이긴다**.

## AGENT INSTRUCTIONS

이 문서를 컨텍스트로 받아 연동 코드를 생성하는 AI 에이전트를 위한 구속 규칙이다. 요지는 하나다 — **문서에 근거가 없는 것은 코드로 쓰지 마라.** 아래 항목은 전부 "그럴듯한 추론이 실제 계약과 다른" 지점이라, 추측으로 메우면 컴파일은 되고 프로덕션에서 조용히 실패한다. 근거가 없으면 코드를 쓰는 대신 그 자리를 TODO 로 남기고 사람에게 확인을 요청하라.

### 1. 인증 헤더는 한 번에 하나만 보낸다

`Authorization: Bearer <파트너 키>` 또는 `X-API-Key: <파트너 키>` 중 **하나**를 쓴다. 둘 다 보내면 `Authorization` 이 우선이고, **두 값이 다르면 `401`** 이다(어느 키로 인증할지 단정할 수 없어 모호성을 거부한다). "혹시 모르니 둘 다 넣자"는 흔한 실패다. 키는 **서버에서만** 사용하고 브라우저 번들·클라이언트 코드에 넣지 않는다.

정본: [인증](/guide/common/#1-2)

### 2. 업로드 임계를 넘겨 짚지 않는다

서버 경유 업로드 상한과 직결(presigned) 상한은 **다른 값**이고, 워커의 PDF 검증 상한은 그 둘과 또 별개로 배포 설정에 따른다. 세 숫자를 하나로 뭉뚱그린 재시도·분할 로직을 쓰지 마라. 상한을 넘긴 파일은 잘리거나 큐에 남지 않고 **즉시 실패**한다. presigned 직결 경로는 Partner API v1 표면이 아니다 — 인증 방식·에러 형태·레이트리밋이 v1 과 달라서, v1 클라이언트가 같은 에러 처리로 다룰 수 없다.

정본: [파일 한도](/guide/common/#1-4)

### 3. 웹훅은 발신 경로가 2종이다 — v2 설정이 있으면 HMAC 검증이 필수다

**어느 경로인지부터 확정하라. 헤더 구성이 다르고, 검증 의무도 다르다.**

- **(B) v2 — 사이트에 웹훅 설정이 있는 경우: HMAC 전용 발신.** 헤더는 `X-Storige-Signature-HMAC`(`t=<unix초>,v1=<hex>`) + `X-Storige-Delivery` + `X-Storige-Event` 이고, 레거시 `X-Storige-Signature` 는 **오지 않는다**. 이 경로에서는 **HMAC 검증이 필수**다 — 검증 없이 처리하는 수신부를 만들지 마라. 서명 대상 문자열은 `{t}.{identifier}:{event}:{timestamp}` 이며 raw body 해시가 아니다.
- **(A) 레거시 — 설정이 없는 사이트로의 폴백.** `X-Storige-Signature` 는 **인코딩이지 서명이 아니라 위조 가능**하다. 이 헤더가 맞았다는 이유로 요청을 신뢰하면 안 된다.

**신규 연동은 (B) 를 쓴다.** `PUT /api/v1/webhooks/config` 로 설정을 발급받아 HMAC 검증을 구현하라. 응답의 secret 은 **발급/회전 응답에서 1회만** 노출되고 재조회할 수 없다 — 받는 즉시 보관하는 코드까지 같이 써라. 어느 경로인지 모르는 채 "특정 헤더가 반드시 온다"고 가정하고 파싱하지 마라.

HMAC 을 검증하더라도 다음은 **두 경로 모두에 그대로 적용된다.**

1. 웹훅을 받으면 **즉시 2xx 를 반환**한다(무거운 처리는 큐로 넘긴다). **중복을 단락했을 때도 2xx** 다.
2. **서명은 본문을 덮지 않는다.** `status`·`outputFileId`·`result` 같은 본문 필드는 서명 밖이다. 페이로드를 **믿지 말고** 식별자만 꺼내 조회 API 로 **재조회**해서 권위 있는 상태를 확정하고, 결제·발주 같은 부수효과의 근거는 재조회에서 취한다. 수신 엔드포인트는 HTTPS 여야 한다.
3. 같은 이벤트가 두 번 올 수 있다(재시도 존재). 중복 판별 키는 `X-Storige-Delivery` 이고 **`jobId` 가 아니다**(한 잡이 여러 이벤트를 발신하므로 정상 이벤트를 삼킨다). 레거시 경로에는 배달 uid 자체가 없으니 **자체 도메인 멱등**을 병행하라.
4. 신선도는 서명 헤더의 `t` 로 판정한다. **본문 `timestamp` 로 판정하지 마라** — 재시도가 정상인데도 거부된다.
5. 모르는 이벤트에서 예외를 던지지 마라. 5xx 가 되어 서버가 재시도를 반복한다.

그리고 콜백 URL 호스트가 등록돼 있지 않으면 웹훅은 **무음으로 전송되지 않는다** — 오류 응답이 오는 게 아니라 아무 요청도 오지 않는다. 웹훅만 기다리는 설계는 이 경우 영원히 멈춘다.

정본: [Webhook 서명 검증](/reference/#5-2)

### 4. 응답 `data` 안쪽 필드를 지어내지 않는다

응답 **봉투**(성공/실패 구분, 에러 코드 자리)는 파트너 대면 계약으로 고정돼 있다. 그러나 그 안쪽 `data` 의 스키마는 **공개 스펙에 존재하지 않는다** — 서버에 응답 타입 선언이 없어서 자동 생성 스펙에도 실리지 않는다. 따라서:

- API 레퍼런스의 상태코드는 **"선언된 응답"** 이지 일어날 수 있는 전체 목록이 아니다. 거기 없는 코드도 온다.
- 응답 예시·응답 타입이 문서에 없는 것은 누락이 아니라 **없다는 사실**이다. `data.url`, `data.items[]` 같은 필드명을 상상해서 파싱 코드나 타입 정의를 만들지 마라.
- 실제 응답을 한 번 받아 확인한 뒤 확정하고, 그때까지는 파싱을 방어적으로(키 부재 허용) 쓴다.

정본: [에러 · 레이트리밋](/guide/common/#1-6)

### 5. 멀티파트 업로드에 `Idempotency-Key` 를 붙이지 않는다

멱등 처리기가 멀티파트 파서보다 **먼저** 실행돼 요청 본문을 보지 못한다. 그래서 파일이 달라도 요청 지문이 같아지고, **같은 키로 다른 파일을 올리면 첫 요청의 응답이 그대로 재전달된다 — 두 번째 파일은 오류 없이 유실된다.** 파일 업로드에는 이 헤더를 생략하거나, 업로드마다 반드시 유니크한 값을 쓴다. JSON 본문 POST 에는 정상 동작하니 그쪽에만 쓰라.

정본: [멀티파트 업로드 계약](/guide/self-editor/#2-0)

### 6. 미구현 기능을 있는 것처럼 쓰지 않는다

- `creationType` 의 `TEMPLATE` · `MIX_COVER_TEMPLATE` 은 미구현이다. **거부 시점을 착각하지 마라 — 생성은 `201` 로 통과해 DRAFT 가 만들어지고, `422` 는 최종화 착수에서 나온다**(`ERR_ASSETS_INCOMPLETE` / `TEMPLATE_COVER_NOT_RENDERED`). 즉 "생성이 성공했으니 지원된다"는 런타임 판정은 틀리고, 사전 필터 없이 이 유형을 흘리면 최종화될 수 없는 DRAFT 만 쌓인다. 스펙의 enum 에 값이 있다는 이유로 코드 경로를 만들지 마라.
- Partner API v1 에는 **편집기 임베드용 엔드포인트가 없다.** 임베드는 편집기 URL + postMessage 규약이며 v1 API 로 생성·제어할 수 없다. `/api/v1/embed` 류의 경로를 만들어내지 마라 — 존재하지 않는다. → [유형 2](/guide/embed/)
- 임베드 편집 + 외부가 합성 결과만 수신하는 유형 3 은 **계약이 없는 제안 단계**다. → [유형 3](/guide/type3/)
- 공식 클라이언트 SDK 는 **npm 에 배포돼 있지 않다.** `npm i` 로 설치하는 패키지를 전제로 한 설치 안내나 import 문을 쓰지 말고 HTTP 로 직접 호출하라.

### 7. 레이트리밋과 스트림 응답

- `429` 를 받으면 `Retry-After` 를 지켜 재시도한다. **`X-RateLimit-*` 헤더는 없다** — 남은 쿼터를 헤더에서 읽는 코드는 항상 `undefined` 를 읽는다.
- 최종 PDF 다운로드는 JSON 봉투가 아니라 **raw `application/pdf` 스트림**이고, 오류일 때만 JSON 이 온다. 응답을 무조건 `JSON.parse` 하지 말고 `Content-Type` 으로 분기하라.

정본: [에러 · 레이트리밋](/guide/common/#1-6)
